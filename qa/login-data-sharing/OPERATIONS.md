# 로그인 데이터 공유 장애 운영 진단 및 설정 복구

관련 Issue: #320, #321, #322, #323. Trouble Shooting 본문은 지정된 Notion 상단 템플릿으로 별도 관리.

## 대상과 안전 원칙

- 기본 도구는 `infra/scripts/login-sharing-diagnose.sh`, SQL 본문은 같은 디렉터리의 `login-sharing-diagnose.sql` 사용.
- 최종 데이터셋 ID와 실제 데이터 소유 사용자 ID를 각각 명시. 카카오 로그인 사용자 ID와 소유 사용자 ID의 혼동 금지.
- 진단 트랜잭션은 `REPEATABLE READ READ ONLY`, 마지막 `ROLLBACK`. 운영 복구·계정 재병합·키 복호화 기능 부재.
- 키 ID·상태·지문 존재 여부만 출력. 키 원문·암호문·전체 지문·OAuth ID·계정 식별자·감사 JSON 원문 미출력.
- 진단 결과에도 내부 사용자 ID 등 개인정보 포함 가능. 접근 제한된 증거 저장소 사용 및 외부 공개 전 검토.
- 비밀번호는 환경변수 또는 로컬 `PGPASSFILE`만 사용. CLI 인수·명령 기록·`set -x`·Issue·Notion에 비밀값 기재 금지.

## 실행

사용자에게서 전달받은 접속 설정을 현재 셸 환경에 별도 주입한 뒤 실행. 비밀값 기본값 없음. `PGDATABASE`는 실제 접속 대상을 명시하며 테스트 DB 이름도 허용. 출력 첫 행의 DB명·스키마·시각·읽기 전용 상태 대조 필수.

필수 환경변수: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` 또는 로컬 `PGPASSFILE`. `PGPASSFILE`은 libpq 기준 권한 600 적용. Docker 모드에는 `PGPASSWORD` 필수.

```bash
# 로컬 psql: 이미 설정된 libpq 환경 사용
bash infra/scripts/login-sharing-diagnose.sh 3 2

# 서버에서 Docker PostgreSQL에 접속: 컨테이너 내부 기준 PGHOST/PGPORT 설정 필요
bash infra/scripts/login-sharing-diagnose.sh 3 2 --docker maple-postgres
```

원격 환경에서는 기존 SSH 절차로 서버에 접속한 뒤 동일 도구 실행. 비밀번호를 SSH 명령 인수에 삽입하거나 셸 명령 문자열로 조합하는 방식 금지. 진단 wrapper는 Docker에 환경변수 **이름**만 전달. DB 컨테이너명은 실제 확인한 이름 사용.

독립 psql 실행 시 `owner_id`와 `context_id` 변수 필수:

```bash
psql -X --no-password --set=ON_ERROR_STOP=1 --set=owner_id=3 --set=context_id=2 \
  --file=infra/scripts/login-sharing-diagnose.sql
```

이 SQL에는 psql의 `\gset`, `\if`, `\gexec` 사용. 일반 JDBC SQL 창에서 전체 실행 불가. 대상 소유자 불일치 또는 이미 병합된 데이터셋 입력 시 비정상 종료. 신규 출처·감사 테이블 부재 시 이관 전 상태로 표시하며 나머지 조회 계속 진행. V18 이하의 더 오래된 스키마는 지원 대상 제외.

## 배포 전후 대조

1. 관련 Issue·PR 템플릿 및 실제 배포 커밋 확인. 진단으로 DB명·최종 데이터셋·실제 소유자·접근 사용자·키 행 ID 확인.
2. 마이그레이션 전 별도 보안 경로에 새 DB 백업 확보. 기존 일일·주간 백업의 파일 존재 여부와 복원 가능 여부 확인. `/backups` 디렉터리의 존재만으로 백업 성공으로 판단 금지.
3. 백업은 운영 DB에 복원하지 않고 격리된 독립 DB에서 먼저 복원 검증. `infra/scripts/restore.sh`의 운영 전체 DB 복원은 이번 설정 복구 용도로 사용 금지.
4. 동일 대상의 진단 결과 저장. 캐릭터·즐겨찾기, 각 사용자/캐릭터 종속 테이블, 월간 하위 스냅샷 수와 provenance 출처 대조. 신규 테이블은 이관 전 부재, 이관 후 존재 확인.
5. 정상 배포 절차로 스키마·애플리케이션 적용. 같은 진단을 재실행하여 키 행·기록 수의 비의도 감소 여부 확인. 변경 없는 반복 진단의 데이터 동일성 검증.
6. 카카오와 각 키로 재로그인 후 데이터셋·설정·사냥/보스 기록 확인. 고유 키 수는 목록 API로 확인. 지문 미등록 행이 있으면 진단의 `known_distinct_keys`만으로 실제 고유 키 수 확정 금지.
7. 감사 요약에서 병합 ID·시각·당사자 확인. 접근 제한된 DB 조회로 해당 감사 JSON의 설정·출처·결정 사유 대조 후 공개 TS에는 비밀값 제외한 결과만 기록.

## 과거 설정 원본 확보 시 선택 복구

원본의 우선 근거는 병합 전 검증된 백업 또는 당시 설정 응답·사용자 확인 자료. 활동 기록, 닉네임 일치, 현재 `updated_at`만으로 과거 설정을 추정하는 복구 금지.

1. 원본을 격리 DB에서 확인한 뒤 복구 매니페스트 작성: 근거 자료 ID·수집 시각, 대상 owner/context, **정확한 OCID**, 현재 기대값, 원하는 즐겨찾기·순서·월드 값. 빈 목록·`false`도 명시. 토큰이나 API KEY 포함 금지.
2. 변경 없는 사전 점검으로 OCID를 현재 소유자 캐릭터 ID에 매핑. 각 OCID가 정확히 1개 존재하며 현재 `user_id`가 대상 owner인지 확인. 누락·중복·다른 소유자·최종 데이터셋 변경 시 중단.
3. 현재 전체 설정과 매니페스트의 기대값 비교. 이미 원하는 상태면 성공으로 종료하여 추가 쓰기 생략. 현재 상태가 기대값도 원하는 값도 아니면 경쟁 변경으로 간주하여 중단. 부분 복구가 아니라 최종 즐겨찾기 전체 집합을 계산하고 18명 초과 시 중단.
4. 사용자 수정·자동 동기화가 없는 작업 구간 확보 후 대상 계정으로 앱의 기존 설정 화면에서 저장. 로그인 신원과 선택된 계정 재확인. 저장 직전 기대값 재조회·대조 필수. 이 절차는 여러 요청을 하나의 DB 원자 작업으로 보장하지 않으므로 동시 쓰기를 차단할 수 없으면 복구 중단.
5. 기존 `PUT /api/v1/characters/preferences` 등 소유권·정원 검증이 있는 설정 경로 사용. DB 직접 `UPDATE`로 출처 메타데이터를 우회하는 방식 금지. 화면에서 검증 가능한 범위로만 복구.
6. 복구 후 진단 및 설정 응답 재조회. 설정·출처 상태와 기록 수 대조. 재실행 시 원하는 상태 확인 후 저장 생략. 카카오·각 API KEY 재로그인으로 결과 확인.

원본에서 OCID 또는 기대 상태를 확인할 수 없거나 동시 수정 통제가 불가능하면 자동 선택 복구 대상 제외. 향후 원자적 복구 도구가 필요하면 별도 Issue·리뷰·독립 DB 검증을 거친 도구만 사용.
